# LLM 上下文超限处理方案调研

> 调研目标：调研 LLM 输入超出模型上下文窗口时的常见处理方案，分析各方案的适用场景和利弊，为本项目 LLM 层设计提供依据。
> 调研时间：2026-08-26

---

## 一、问题背景

LLM 的上下文窗口（context window）是有限的。当输入 token + 预留输出 token 超过模型 context_length 时，API 会直接报错拒绝请求。

本项目使用云端模型（豆包 seed-2-1-pro 256K、DeepSeek 128K），教学视频 ASR 全文通常 1-3 万字（约 1-2 万 token），常规情况不会超限，但极端长视频（2小时以上）可能超限。需要确定超限后的处理策略。

---

## 二、方案总览

| 方案 | 原理 | 成本 | 延迟 | 信息保留 | 跨块推理 | 适用场景 |
|---|---|---|---|---|---|---|
| 直接截断 | 丢弃超出部分 | 零 | 零 | 差（直接丢失） | 不涉及 | 关键信息集中在开头/结尾 |
| MapReduce 分块 | 分块独立处理→合并结果 | 中高（多次调用） | 中（可并行） | 中（合并可能丢细节） | 弱 | 信息提取、摘要 |
| 滑动窗口 | 分块+重叠保留上下文 | 中高（重叠重复计算） | 中 | 中 | 弱（仅相邻块） | 顺序处理、对话 |
| 摘要压缩 | 先压缩旧内容再注入 | 中（额外摘要调用） | 中 | 中（摘要可能丢细节/幻觉） | 中 | 长对话历史 |
| 分层递归摘要 | 多层 MapReduce 逐层摘要 | 高 | 高 | 中低（逐层损失） | 弱 | 超长文档（500K+） |
| RAG 检索 | 分块索引，只注入相关片段 | 中（需向量库） | 低（检索快） | 取决于检索质量 | 不涉及 | 问答系统、知识库 |
| 语义分块 | 按语义边界而非固定长度分块 | 中（需 embedding） | 中 | 较好 | 弱 | 结构化文档 |
| Prompt 压缩 | 用专门模型压缩 prompt | 中（需压缩模型） | 低 | 中（压缩率 6x-480x） | 不涉及 | 前沿研究阶段 |
| 换长上下文模型 | 直接用 256K/1M 模型 | 高（模型贵） | 低 | 好 | 好 | 预算充足 |

## 三、各方案详细说明

### 1. 直接截断（Truncation）

**做法**：输入超限时直接丢弃超出部分。可选择从头截断（保留尾部）、从尾截断（保留头部）、或截断中间（保留首尾）。

**优点**：
- 零额外成本、零额外延迟
- 实现最简单

**缺点**：
- 直接丢失信息，可能截断关键内容
- 截断位置不可控，可能切断语义

**适用**：关键信息集中在文本开头或结尾的场景。研究表明，对于部分内容生成任务，简单截断的效果甚至优于复杂分块（文档开头往往包含足够信息）。

**生产实践**：Microsoft Agent Framework 将截断策略定位为"紧急兜底"（emergency token-budget backstop），不作为常规策略。

### 2. MapReduce 分块（Divide and Conquer）

**做法**：
- **Map 阶段**：将长文本按固定长度或语义边界分成多个块，每块独立调用 LLM 处理
- **Reduce 阶段**：将各块的结果合并成最终结果

**优点**：
- 可处理任意长度输入
- Map 阶段可并行执行，延迟可控
- 每块都在上下文窗口内，不会超限

**缺点**：
- 多次 LLM 调用，token 成本增加
- **跨块推理能力弱**：没有任何一次调用能看到完整文本，跨越两个块的信息可能丢失
- Reduce 合并逻辑是任务特定的，不同任务需要不同的合并策略
- 各块独立处理可能产生冲突结果

**学术进展**：
- **LLM×MapReduce**（arXiv 2410.09342）：引入结构化信息协议和上下文置信度校准机制，解决块间依赖和冲突问题
- **ToM（Tree-oriented MapReduce）**（EMNLP 2025）：利用文档层级结构（标题/子标题）构建文档树，自底向上聚合，支持递归推理

**适用**：信息提取、摘要等"各块独立处理后合并"的任务。

### 3. 滑动窗口（Sliding Window）

**做法**：分块时块与块之间保留 10-20% 的重叠，保证块边界处的上下文连续。

**优点**：
- 比简单分块保留更多上下文连续性
- 实现相对简单

**缺点**：
- 重叠部分重复发送给 LLM，token 消耗增加
- 只能保证相邻块的上下文，远距离跨块推理仍然丢失
- 重叠大小需要调优

**适用**：顺序处理任务、对话历史管理。

### 4. 摘要压缩（Summarization Compression）

**做法**：
- 当上下文接近限制时，将最早的内容用 LLM 生成摘要，用摘要替换原文
- 最近的内容保留原文
- 可递归执行：摘要太长就再摘要

**优点**：
- 保留全局信息（相比直接截断）
- token 数量显著减少

**缺点**：
- 摘要本身是一次 LLM 调用，增加成本和延迟
- **摘要可能引入幻觉**或丢失关键细节
- 摘要质量直接影响后续处理质量
- 压缩是有损的

**生产实践**：
- Microsoft Agent Framework 的 `SummarizationCompactionStrategy`：当上下文达到阈值（如 70%）时，将最早的 N 条消息压缩成摘要，保留最近 K 条原文
- 摘要 prompt 必须明确要求保留：已做决策、承诺、已确认事实、未解决问题

**适用**：长对话历史管理、多轮 Agent 场景。

### 5. 分层递归摘要（Hierarchical Summarization）

**做法**：MapReduce 的进阶版。文本分块→每块摘要→摘要分组→再摘要→直到适合一个上下文窗口。

**优点**：
- 可处理超长文档（500K-5M token）

**缺点**：
- 成本最高、延迟最长
- 信息逐层损失，底层细节可能完全丢失
- 适合生成概览，不适合精确提取

**适用**：超长文档概览、多文档合并摘要。

### 6. RAG（检索增强生成）

**做法**：
- 将文本分块后向量化存入向量数据库
- 用户提问时检索最相关的 K 个片段
- 只将检索到的片段注入上下文

**优点**：
- 上下文长度可控，只注入相关内容
- 可扩展到任意规模的语料库

**缺点**：
- 需要向量数据库和 embedding 模型，架构复杂
- 检索质量决定效果，可能漏检关键片段
- 不适合"需要看到全文才能完成"的任务

**适用**：问答系统、知识库查询。**不适合需要全文处理的任务**（如全文纠错、全文知识点提取）。

### 7. 语义分块（Semantic Chunking）

**做法**：不按固定 token 数分块，而是按语义边界分块——计算相邻句子的 embedding 相似度，在语义变化大的地方断开。

**优点**：
- 保持语义完整性，不会切断一个完整的话题
- 块大小自适应内容密度

**缺点**：
- 需要 embedding 模型计算，增加预处理成本
- 2026 年研究表明，对于部分任务语义分块相比简单截断没有显著提升

**适用**：结构化文档（有标题、段落的文档）。

### 8. Prompt 压缩

**做法**：用专门的压缩模型（如 LLMLingua、500xCompressor、ChunkKV）对 prompt 进行压缩，去除冗余 token，保留关键信息。

**优点**：
- 压缩率极高（6x-480x）
- 不需要多次调用主 LLM

**缺点**：
- 需要额外的压缩模型，部分方案需要微调
- 大多处于研究阶段，生产成熟度低
- 压缩是有损的，可能影响精度

**适用**：前沿研究，暂不建议生产使用。

### 9. 换长上下文模型

**做法**：直接使用上下文窗口更大的模型（如豆包 256K、Gemini 1M）。

**优点**：
- 最简单，不需要任何分段逻辑
- 全文可见，跨区域推理能力最好

**缺点**：
- 长上下文模型通常更贵
- **"Lost in the Middle" 现象**：研究表明，128K 上下文时模型对中间内容的准确率仅 58%（开头 80%、结尾 82%）
- 长上下文推理延迟更高

**适用**：预算充足、文本不超过模型上下文上限。

## 四、本项目场景分析

### 我们的任务特点

| 任务 | 输入 | 需要全文可见？ | 输出 | 合并难度 |
|---|---|---|---|---|
| ASR 纠错 | ASR 全文 | 是（纠错需上下文） | 纠错后全文 | 低（直接拼接） |
| 知识点提取 | ASR 全文 | 是（不能遗漏知识点） | 知识点列表 | 中（合并去重） |
| 题目提取 | ASR 全文 | 是（不能遗漏题目） | 题目列表 | 中（合并去重） |
| 思维导图 | 知识点列表 | 否（输入已是结构化数据） | OPML | 不需要 |

### 关键约束

1. **我们是批处理工具，不是问答系统**——RAG 不适用，因为任务需要看到全文而非检索片段
2. **豆包 256K 上下文**——约 15-20 万汉字，覆盖绝大多数教学视频（30-60 分钟约 1-3 万字）
3. **不能丢内容**——纠错、知识点提取、题目提取都要求完整覆盖全文
4. **合并逻辑是任务特定的**——纠错可直接拼接，知识点/题目提取需要去重合并

### 超限概率评估

- 30 分钟视频：约 1-1.5 万字 ≈ 0.7-1 万 token → 远低于 256K
- 60 分钟视频：约 2-3 万字 ≈ 1.5-2 万 token → 远低于 256K
- 2 小时视频：约 5-6 万字 ≈ 3-4 万 token → 仍低于 256K
- **5 小时以上视频**才可能接近 256K 限制，这种情况极少

## 五、建议方案

### 分层策略

```
输入文本
  │
  ├─ token 估算 ≤ context_length（留足输出空间）
  │    └─ 直接调用，不做任何处理
  │
  ├─ token 估算 > context_length
  │    └─ MapReduce 分块处理
  │         ├─ 按语义边界（段落/句子）分块
  │         ├─ 每块独立调用 LLM
  │         └─ 合并结果（合并逻辑由业务模块提供）
  │
  └─ 分块后单块仍超限（极端情况）
       └─ 报错，提示视频过长
```

### 设计要点

**1. LLM 层提供分块调用机制，不提供合并逻辑**

MapReduce 的 Map 阶段（分块、逐块调用）是通用能力，由 LLM 层提供。但 Reduce 阶段（合并结果）是任务特定的——纠错直接拼接，知识点提取需要去重。LLM 层无法也不应该知道如何合并，合并函数由业务模块注入。

**2. 分块策略：按语义边界，不用固定 token 切割**

ASR 文本有自然的句子和段落边界。按句子/段落边界分块，避免切断语义。块大小留 20% 余量给输出。

**3. 不做摘要压缩、不做 RAG**

- 摘要压缩有损且可能引入幻觉，不适合纠错和精确提取任务
- RAG 是问答场景的方案，不适合全文处理任务
- 我们的超限概率低，不需要复杂方案

**4. 准确的 token 估算是第一道防线**

在调用前准确估算输入 token，预留输出空间（模型 max_output），只有真正超限才触发分块。

### 方案的局限性（诚实说明）

MapReduce 分块处理有一个固有缺陷：**跨块推理能力弱**。如果一个知识点或题目的讲解跨越了两个块的边界，分块处理可能导致重复提取或遗漏。这是 MapReduce 方案的固有 trade-off，在我们的场景中：

- 知识点/题目提取：通过业务模块的去重合并逻辑可以缓解
- ASR 纠错：纠错主要依赖局部上下文，跨块影响小
- 如果未来需要更强的跨块推理能力，可以考虑 ToM（树状 MapReduce）等进阶方案
